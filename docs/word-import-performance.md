# DOCX 导入性能对比

本次对比测量单次导入的 XML 缓存、CRC 查表优化前后，真实 TypeScript
DOCX 导入器处理相同文件的耗时。两版代码在同一个 Chromium 进程中运行。
测量范围不含完整应用打开、Tauri IPC、原生 WebView、Rust 解包和编辑器渲染。

此前新建独立 Word 标签页时，`App.vue` 会导入文件以检查兼容性，随后丢弃模型；
`StandaloneWordEditor.vue` 挂载时再次导入。同一次打开因此重复执行完整导入链路。
已验证模型的一次性交接属于另一个集成优化，其调用次数需要单独的集成证据；
本文的编解码器耗时不能证明完整应用打开速度的变化。

## 正式结果（2026-10-14）

正式运行时间为 UTC 19:55:33–19:59:28。环境为 Linux x86_64、Xeon Platinum 8573C、
3 个可见逻辑 CPU（进程可用并行度 2）、Chromium 154.0.8037.57、Node 24.19.0。
测量期间未并发运行其他项目测试或构建。四个样例全部通过，当前源码和基线快照哈希
在运行前后相同，无浏览器错误或外部请求。原始数据见
[完整结果 JSON](word-import-performance-results.json)。

以下单位均为毫秒；箭头表示优化前 → 优化后。

| 样例 | 路径 | 中位数 | P95 | 中位数降幅 |
| --- | --- | ---: | ---: | ---: |
| 原生纯文本（4 段） | 浏览器完整导入 | 10.62 → 7.62 | 22.26 → 11.62 | 28.2% |
| 原生纯文本（4 段） | 已解包语义导入 | 4.07 → 2.84 | 15.50 → 8.29 | 30.2% |
| 构造 100 段 | 浏览器完整导入 | 22.95 → 16.17 | 33.57 → 20.52 | 29.5% |
| 构造 100 段 | 已解包语义导入 | 12.74 → 11.07 | 16.14 → 19.96 | 13.1% |
| 构造 1,000 段 | 浏览器完整导入 | 203.90 → 127.30 | 310.60 → 237.10 | 37.6% |
| 构造 1,000 段 | 已解包语义导入 | 133.20 → 105.35 | 196.25 → 146.15 | 20.9% |
| 构造 4,000 段 | 浏览器完整导入 | 848.75 → 502.40 | 1054.40 → 627.95 | 40.8% |
| 构造 4,000 段 | 已解包语义导入 | 519.15 → 443.50 | 769.65 → 796.10 | 14.6% |

4,000 段样例为 219,727 个 UTF-16 代码单元、72,028 字节 ZIP、1,731,290 字节
解压内容。浏览器完整导入中位数下降 40.8%；桌面解包后的同一语义路径下降 14.6%。
后者仍是 JavaScript/DOM 处理，不代表 Rust 核心或整个桌面应用加速 14.6%。
浏览器结果包含 XML 缓存和 CRC 查表共同生效的收益，未对两项优化单独归因。

100 段和 4,000 段的已解包语义路径 P95 在本次运行中上升，因此不能声称所有分位数
都得到改善。25 个批次的完整样本已保留；没有通过重复运行挑选更好的结果。

XML 解析次数另行测得：原生 11 部件样例的浏览器路径从 33 次降为 11 次，
已解包语义路径从 22 次降为 11 次；三个构造样例均为 6 部件，对应从 18 次降为
6 次、从 12 次降为 6 次。四条导入路径在计时前后得到完全一致的完整模型 JSON。

输入 DOCX、每个部件的 SHA-256、完整模型 JSON 的 SHA-256，以及冻结基线源码归档
位于 `test-results/word-import-performance/`。稳定 JSON 档案保留全部原始样本、
环境与源码哈希；运行脚本为 [benchmark-word-import.cjs](../scripts/benchmark-word-import.cjs)。

## 测量范围

| 路径 | 包含 | 不包含 |
| --- | --- | --- |
| `importWordDocument` | 浏览器 ZIP 检查、有上限的解压、CRC 校验、XML 校验、OOXML 解析和规范化模型创建 | 文件读取、界面、base64 传输、原生代码 |
| `importWordParts` | 已解码部件 Map 的校验、XML 校验、OOXML 解析和规范化模型创建 | Rust ZIP 处理、JSON/base64 传输与解码、界面 |

旧桌面导入器先解析所有 XML 部件以校验结构，再为语义读取重新解析；旧浏览器导入器
在 ZIP 读取阶段还会额外解析一遍。新缓存只在一次导入内生效，后续调用仍会重新校验
调用方提供的字节数组。Rust 仍负责 ZIP 容器校验，不负责 XML 解析。
XML DOM 缓存保留至当前导入结束，待交接模型仅保留至编辑器消费或取消，没有跨文档
持久缓存。本次未测峰值内存，耗时下降不能用于推导内存占用下降。

桌面协议目前仍需将 ZIP 编成 base64 传给 Rust，在 Rust 中解码、解压，再将各部件
编成 base64，通过 JSON 数组返回 JavaScript 解码。取消第二次导入可以减少一遍这条
链路。本文既未测量这条跨边界链路，也不会将独立微基准的中位数相加来推算 IPC 收益。

## 集成与兼容性证据

[`independent-word-import-performance.cjs`](../tests/browser/independent-word-import-performance.cjs)
在真实 Chromium 应用和文件选择流程中完成 5 组检查，使用真实 runtime 模块，
没有替换导入函数：12 部件样例首次打开及再次作为新标签打开均只解析 XML 12 次，每个
部件各一次；切回已编辑标签页时读取保存的当前快照，10 个部件各解析一次，编辑内容
得以保留。这里只统计导入调用栈，排除了保存快照时的 XML 校验。这是浏览器流程的
解析次数证据，不是原生 Tauri IPC 计数或延迟测量。

同一套检查验证：修改 Map 内的部件、原位修改同一个 Uint8Array，以及修复损坏 XML
后再次导入，都不会读到上一调用的缓存；未引用的 XML/rels 中的非法结构、DTD、
UTF-8/UTF-16 编码问题仍在 20 条负例路径上被拒绝。另有 8 个独立生成的 ZIP 正例
及 8 个伪造 CRC 反例，覆盖 stored/deflate、头部/descriptor 和跨多个输入块的解压，
通过 Python `zipfile` 与 `zlib.crc32` 独立核对。

应用状态测试通过 81 项，覆盖交接的 id/base64 精确匹配、一次性消费、失败与关闭
清理，以及异步加载源改变等生命周期。独立编辑器真实应用回归通过 13 项，包含不支持
文件拒绝后保留当前未保存文档、保存后重开、编辑及标签页切换。这些结果支持兼容性和
状态管理判断，不用于推算打开速度。

## 复现与校验

在仓库根目录运行，指定不可变的优化前源码快照：

```sh
WORD_IMPORT_BASELINE=/path/to/baseline node scripts/benchmark-word-import.cjs
```

快照包含 `manifest.json`（相对路径到 SHA-256 的映射）及对应源码。脚本检查所有
快照文件，并归档到 `test-results/word-import-performance/baseline-source/`。
这个归档目录也可作为 `WORD_IMPORT_BASELINE` 再次运行。对比仅加载快照中的
`docx.ts` 和 `model.ts`；未改动的辅助模块由两版共享并记录哈希。脚本将基线导入器
的模型引用指向冻结版本，其余被测函数没有改写。报告记录原始源码及实际加载基线源码
的哈希。

快速检查脚本是否可运行时，可用 smoke 模式；其耗时不用于发布性能结论：

```sh
WORD_IMPORT_BENCH_SMOKE=1 WORD_IMPORT_BENCH_OUTPUT=/tmp/word-import-smoke node scripts/benchmark-word-import.cjs
```

正式测量包含一个保留原始字节的 LibreOffice 原生纯文本样例，以及项目自行构造的
100、1,000、4,000 段双语文档。构造文档使用冻结基线导出器、fflate level 1 压缩和
固定 ZIP 时间戳，不把它们当作原生 Office 作者来源。报告保留输入 DOCX、部件哈希、
源码哈希和所有原始耗时样本。

四条被测路径使用相同 ZIP 字节或已解码部件 Map。计时前后都要求完整文档模型的
规范化 JSON 完全一致，包含段落标记、直接格式、来源样式、段落 ID 和保留的元数据；
不删除任何字段。DOMParser 次数另行插桩统计，所有计时前恢复原方法。样例解码、
模型对比和 JSON 序列化均不计入被测函数耗时。

正式运行预热 5 批，测量 25 批。小 ZIP 每批调用 10 次，大 ZIP 每批调用 2 次，
基线和当前版本的先后顺序逐批交替。中位数和 P95 均基于每批的单次平均耗时；P95
采用最近秩法，即排序后第 24 个样本，不代表单次调用的尾延迟。不强制触发垃圾回收。
报告记录机器与运行时、负载、起止时间、浏览器错误和外部请求；正式运行期间当前源码
和基线快照哈希必须保持不变。

结果只描述本次环境。XML 解析次数和完整模型一致性是确定性检查，耗时则受机器、
浏览器、文档内容、内存分配和垃圾回收影响。这四个性能样例之外的兼容性由编解码器
与原生语料回归测试验证。
