# Calc 首次就绪画面调查

2026-10-14，在本地生产预览构建 `2026.1014.1837` 上完成的八次独立实验均为 **`ok: false`**。目前没有可以合入产品的首帧修复。本文补充 [鼠标时间戳修复记录](calc-input-fix.md)，不改变该记录的历史版本、六个成功场景或未完成场景 E。

每次使用全新的 Chromium 上下文，视口 1560 × 1000、DPR 1。页面首次显示就绪后立即截图，从截图中的颜色标记定位 B2，进行第一次真实点击；只有正确选中 B2 才继续键入和保存。不重复点击、不重新定位后重试、不新增就绪等待。所有报告保留原来的失败结论，`sourceUnchanged: true`；实验未修改产品文件。

## 最后一次 ResizeObserver 实验

该候选仅通过测试路由变换 host，保留每次成功打开后的即时 resize，取消固定 200ms 的第二次触发；DOM 观察到新的正 CSS 尺寸时触发一次 resize。它不修改 canvas 尺寸、worker、焦点、加载遮罩或 ready 判定，也不增加等待。引擎未就绪、没有当前文档、发生适用错误或销毁后均不触发。

## 后续边界

需要区分三件事：**模型可查询、原生尺寸/布局已更新、用户已看到对应画面**。前两者的响应不是第三者的确认。

实际 Emscripten glue 将 DOM resize 回调转发到引擎线程，主线程 `dispatchEvent()` 返回不表示原生处理结束。参考 Qt 源码中，写入 canvas 尺寸、更新窗口几何和发出 expose 后，仍有 `UpdateRequest → QWasmCompositor::frame() → swapBuffers()` 的合成步骤。UNO `XPaintListener` 的通知发生在 VCL 绘制过程中，也不是浏览器呈现完成通知。参考 Qt 提交与当前完整二进制尚未建立逐项对应，不能把源码推导写成已验证的二进制根因。

当前应用适配层没有公开的 paint/presentation completion 握手。ResizeObserver、尺寸一致、UNO 窗口查询、若干次 rAF 或 `processEventsToIdle()` 均不能单独充当这种握手。下一步应先建立能绑定文档与视口版本的原生合成证据，再验证第一帧与第一次输入；不继续用任意延时、重复点击或盲目重试获得通过。
