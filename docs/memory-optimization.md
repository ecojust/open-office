# 内存优化记录（2026-10-13）

本轮修复了关闭最后一个 Office 标签、仍保留 PDF 标签时，隐藏的办公引擎没有卸载的问题，并减少文档传输副本、限制 PDF 渲染缓存。**编辑 Office 文档时的高内存基线尚未解决，不能把本次更新描述为已将约 1.7 GB 降到几百 MB。**

## 修改范围

- Office 标签真正关闭后释放 iframe、请求监听、回调及工作线程。保留着的 Office 标签仍可在 PDF 与 Office 间切换；未保存确认、保存取消和草稿保护保持有效。
- 打开文档、插入图片及导出使用可转移 ArrayBuffer，减少跨窗口复制。中文字体与 MEMFS 共享输入缓冲区，不再保留额外字体副本。引擎的计算并发配置由 4 调为 2；这不是总工作线程数，实测 Calc 的线程池由 5 个降为 4 个。
- PDF 缩略图只保留可见页面的像素；隐藏、滚出或关闭时清空画布。正文和幻灯片单画布限制为 16,777,216 像素，超大页面降低采样密度，导出文件内容不变。
- PDF 文本缓存仅保留当前页；异步加载过期后取消并释放。放映结束释放画布、媒体与临时 URL。
- PDF 撤销与重做共享 8 个状态、48 MiB 字符串估算预算。大文件至少保留最近一步恢复状态，单个状态可以超过软预算；文件仍受 40 MiB 输入上限约束。

## 如何测量

使用实际 Vue 应用，依次打开并导出 Word 富文档、2,000 行 Excel、20 页 PPT，再打开 PDF、关闭 Office、关闭全部标签、重新打开 Word、再次关闭。导出后独立检查 Word 标记、Excel 2,001 行（含标题）、PPT 20 页、PDF 20 页。

环境为 Linux x64、Chromium 154.0.8037.57、1440 × 1000 视口，SwiftShader 软件 WebGL。每阶段等待 5 秒，未强制垃圾回收；第二轮前后对照另在最终关闭后闲置 20 秒。统计浏览器及其渲染、GPU、工具等子进程的 `/proc/PID/smaps_rollup`，以共享页按比例分摊的 PSS 为主要物理指标，RSS 另行记录。排除 Vite、测试脚本及 Python PDF 后端进程，**并非完整 Tauri 应用内存，也不是 macOS M5 或硬件 GPU 测试**。

基线源码为 `29a6208c8ea4eb6358e36826d78d5a546508ca78`。两次优化后测量的生产文件指纹均为 `5321ddcffae93852b3ab25b90c3dd209cbb5f68ccfd687751a4545e8b3b7a6fc`。随后补充了大 PDF 至少一步撤销的保护；该修正单独回归验证，没有重测 Office 物理内存。具体环境、指纹、各阶段及导出结果保存在 [memory-results.json](memory-results.json)。

## 测量结果

下表为 PSS，单位 MiB，四舍五入；区间覆盖两次运行，不是置信区间。

| 阶段 | 修改前两次 | 修改后两次 |
| --- | ---: | ---: |
| 首页 | 367–372 | 371–376 |
| 打开 Word | 1,270–1,273 | 1,256–1,258 |
| 切换 Excel | 1,361–1,428 | 1,385–1,392 |
| 切换 PPT | 1,476–1,478 | 1,433–1,446 |
| 仅剩 PDF 标签 | 1,514–1,605 | 1,367–1,459 |
| 全部关闭 | 1,348–1,458 | 1,257–1,282 |
| 很快重新打开 Office | 1,332–2,182 | 2,086–2,132 |
| 再次关闭，等待 5 秒 | 1,140–2,084 | 479–2,009 |
| 第二轮再闲置 20 秒 | 1,117 | 477 |

可直接验证的生命周期改善：仅剩 PDF 时，基线仍有 1 个 Office iframe、5 个 Office Worker；修改后为 0 个 Office iframe、0 个 Office Worker，只剩 PDF Worker。原版在关闭全部标签后也能退出线程，不能据此断言它永久泄漏。

物理回收时机有明显波动：优化后的首次运行在最后关闭 5 秒后为 479 MiB，第二次同样时点仍为 2,009 MiB，额外闲置后才降至 477 MiB。短时间重开仍可能达到约 2.1 GiB PSS。不能将闲置回收后的数值用作编辑时占用，也不能承诺瞬时回收或稳定百分比降幅。

## 为什么没有直接改 GPU 或 WASM 容量

引擎已经使用 WebGL。CPU 侧文档模型、WASM 代码及缓冲区不会因开启 GPU 而消失；本次软件 WebGL 测试不支持宣称硬件 GPU 的收益。

固定版本 WASM 的共享内存导入同时要求初始和最大 16,384 页，即 1 GiB。仅修改宿主 JavaScript 容量会导致链接失败。映射分析中，1 GiB 线性堆在初次 Word 场景的实际驻留约 214 MiB，因此不能把容量缩小量直接当作物理节省量。大块数据、模块与编译代码也贡献占用。显著降低编辑基线需要另行构建和验证较小的引擎，或调整引擎进程架构；本轮没有替换已固定校验的运行时，也没有通过删除编辑功能换取测试数字。

## 验证与复现

最终源码的 386 项前端/协议单测、28 项 Python PDF 编辑回归及生产构建已通过。另有 7 项 PDF 内存浏览器检查、26 项 PDF 编辑检查、19 项放映检查通过。PDF 专项覆盖 100 页滚动（最多 6 张可见缩略图）、超大页面预算、加载取消及文本缓存竞态；随后补充的大文件撤销保护通过定向与完整单测，没有重复整套浏览器测量。

```bash
npm test
npm run build
npm run test:browser:pdf-memory
MEMORY_RUN=local-check npm run test:browser:office-memory
```

内存测试需要 Linux `/proc`、Playwright Chromium、已准备的 Office 资源、PDF 后端与兼容测试样例。每次使用不同的 `MEMORY_RUN`，避免覆盖报告；`MEMORY_TARGET_ROOT` 可指向单独的基线源码目录。请串行运行内存测试，并记录硬件、进程范围和等待时间。macOS 与 Windows 桌面上的驻留表现需要在对应系统另行验证。
