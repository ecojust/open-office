# 独立文字编辑器的 Rust 实现与性能记录

当前采用逐步迁移方案：首个独立 Rust crate 已负责桌面 DOCX 的 ZIP 解压、压缩与 CRC 校验，通过 Tauri 后台任务接入。Vue 界面、文档模型、OOXML/XML 语义解析和排字仍在前端。下面分别记录已有实现、原始基线与后续工作；目前没有测得 Rust 相对 TypeScript 的端到端提速倍率。

## 已实现的 Rust 模块

`crates/word-package` 不依赖 Tauri 或界面，提供字节缓冲区 API 和 `{name, dataBase64}` 的传输 API。压缩使用 `flate2` 的 Rust 后端；接入命令是 `word_read_package` 与 `word_write_package`，均在 `spawn_blocking` 中运行。该 crate 只处理容器，解包结果仍由同一个 OOXML 编解码器检查 XML、关系、样式及支持范围，原生拒绝不会触发浏览器实现回退。

限制为 ZIP 输入/输出 16 MiB、总展开 32 MiB、每条 4 MiB、256 条。支持 stored/DEFLATE 和标准 data descriptor；校验路径、重复名称、重叠区间、CRC、文件头及实际解压长度，拒绝 ZIP64、分卷和加密。名称上限为 1,024 UTF-8 字节，较原 TypeScript 的 1,024 UTF-16 单位检查更严格。详细接口及复现方式见 [crate README](../crates/word-package/README.md)。

Rust 的 12 组测试、Python `zipfile` 双向互操作及完整 Tauri `cargo check --offline --locked` 已通过。浏览器协议专项使用实际 Rust CLI 验证运行时分支，但传输由测试接管，不能替代真实 Tauri IPC、文件对话框或发布安装包验证。

此前的基线偏移兼容性回归通过了 90 份完整语料对照（73 份接受、17 份语义拒绝），共执行 397 次真实 Rust CLI 调用及 268 次受控 invoke 调用。该轮确认 Rust 包处理与浏览器编解码语义一致，没有重新测量性能，也没有扩大为全 Rust 编辑器；详细范围和源码哈希见[独立编辑器验证记录](independent-word.md#自定义基线偏移迭代的历史记录)。

此前段落间距回归将完整语料扩展到 100 份（81 份接受、19 份语义拒绝），28 组检查共执行 439 次真实 Rust CLI 调用（342 次读取、97 次写入）及 297 次受控 invoke 调用。行距、段落间距与格式来源经过实际包处理后保持一致，损坏容器及不支持的文档语义按各层规则拒绝。该轮没有修改 Rust 核心或重新测量耗时；不能把新增兼容性覆盖视为性能提升。源码、CLI 哈希与失败后重跑记录见[段落间距验证](independent-word.md#段落间距迭代)。

页面设置回归通过 30 组检查，实际处理 126 份完整语料（96 份接受、30 份语义拒绝），执行 525 次真实 Rust CLI 调用（413 次读取、112 次写入）及 355 次受控 invoke 调用。横向纸张、独立方向标志和四边距经过浏览器与 Rust 两条包处理路径后保持一致；合法 ZIP 中不支持的纸型漂移和装订线仍由 XML 层拒绝。报告位于 `test-results/word-page-settings-rust/report.json`，绑定当前编解码、纸型规则与 CLI 哈希。本轮仍未修改 Rust 核心，也没有新的性能或真实 Tauri IPC 测量。

已增加独立 Linux 原生 IPC 验证入口 `npm run test:native:word-package -- --executable /absolute/target/debug/open-office`，覆盖两轮读写、中文与 emoji、上下标／删除线、高亮与背景及无效输入拒绝，并隔离测试数据、核验报告和构建哈希。本次原生编译、35 项 Rust 测试（另 1 项既有冻结 PDF 测试忽略）、72 项应用外壳测试、类型检查和前端构建通过。实际启动在创建 WebView 前失败：系统固定路径 `/usr/lib/x86_64-linux-gnu/webkit2gtk-4.1/WebKitNetworkProcess` 不存在，进程以 SIGTRAP 退出。现有工具链目录中的 WebKit 库不足以替代完整系统安装；本次没有产生 IPC 通过结果。失败记录保存在本地 `test-results/word-package-native/report.json`，补齐系统依赖后可用同一入口复跑。

后续新增[包核心性能诊断](word-package-performance.md)，用优化构建分别测量 Rust 核心、base64 接口、JSON 和常驻子进程传输，与 Chromium 中的实际包读取路径及 fflate 对照。此项把 XML 解析和压缩策略差异单列，不能用核心耗时直接代表完整应用提速。

## 现有性能基线

2026-10-14 在 Linux Chromium 154 中直接运行真实的 TypeScript 模型、DOM 适配与 DOCX 模块，使用中英文合成段落模拟在正文中部输入。输入流程预热 2 次、测量 7 次；文件读写预热 1 次、测量 4 次。下表为中位数。

| 段落数 | 正文长度（UTF-16 单位） | 模拟一次输入处理 | DOCX 导入 | DOCX 导出 |
| --- | ---: | ---: | ---: | ---: |
| 10 | 518 | 1.2 ms | 3.7 ms | 1.1 ms |
| 100 | 5,108 | 6.8 ms | 4.4 ms | 2.0 ms |
| 1,000 | 51,008 | 194.1 ms | 86.1 ms | 27.8 ms |
| 4,000 | 204,008 | 1,017 ms | 135.6 ms | 50.0 ms |

4,000 段场景中，模型复制与 DOM 读取阶段中位数为 820.5 ms，全文 DOM 重建与选区恢复为 165.9 ms，模型提交为 21.9 ms。各阶段独立统计，中位数不必相加等于总耗时。

将脚本整理为仓库内的可复现命令后再次运行，4,000 段输入中位数为 1,028.4 ms、DOCX 导入 152.9 ms、导出 43.4 ms，主要输入成本仍为全文 DOM 读取与重建。上表和原始记录保留第一轮基线；临时输出随复跑覆盖，最终结果另存为下面的对照文件。

这是单机、短样本的模块微基准，不是完整 Vue 应用、真实输入法或桌面安装包的按键延迟测量。它也不包含 Rust、原生 IPC 或 WASM 对照，不能用于宣称语言之间的性能倍率。

原始记录：[word-performance-baseline.json](word-performance-baseline.json)。复现命令：`node scripts/benchmark-independent-word.cjs`，需要依赖已安装及可运行的 Chromium；可用 `PLAYWRIGHT_CHROMIUM_EXECUTABLE` 指定路径。脚本自动启动和关闭本地 Vite，结果写入 `test-results/word-performance-baseline.json`。

## 首轮输入性能对照

首轮产品源码停止修改、其他测试与 Rust 编译结束后，用同一脚本独立复跑。结果包含当时新增的格式与元数据处理开销；这份输入基准早于后续段落缩进及段落样式来源的迭代，后续迭代没有重测输入延迟。新的包核心诊断是另一套独立测量。

| 段落数 | 原输入中位数 / P95 | 首轮优化后输入中位数 / P95 |
| --- | ---: | ---: |
| 10 | 1.2 / 2.1 ms | 0.8 / 1.7 ms |
| 100 | 6.8 / 7.8 ms | 4.9 / 6.5 ms |
| 1,000 | 194.1 / 311.0 ms | 26.2 / 30.8 ms |
| 4,000 | 1,017.0 / 1,123.1 ms | 136.6 / 156.5 ms |

4,000 段、204,008 个 UTF-16 单位的输入路径中位耗时降约 86.6%；DOM 读取阶段从 820.5 降至 50.5 ms，渲染从 165.9 降至 27.0 ms，选区读取从 18.5 降至 1.6 ms。改善来自 TypeScript/DOM 路径调整，不是 Rust 与 TypeScript 的速度对比。脚本仍强制执行渲染，而应用普通输入已跳过重绘；因此这也不能直接当作完整应用键入延迟。

同轮浏览器 DOCX 导入中位数为 189.5 ms、导出为 82.4 ms，比原基线的 135.6 / 50.0 ms 更慢。新增的语义检查与格式保留扩大了工作量，后续应继续独立定位文件读写成本；不能把输入收益推广为所有操作都提速。测量不包含 Rust、base64/IPC、真实系统输入法或原生 WebView。

最终原始记录：[word-performance-after.json](word-performance-after.json)，SHA-256 为 `c56bc777f28effd8bcd8c814e397ae42e47b49514d5a0c0b05785d2e3b5e31e8`。中间一次与代码热更新、其他重负载任务并发的测量未作为最终对照；更早的 88.1 ms 结果不包含最终全部功能，也未用作当前性能结论。

## 已处理与剩余成本

- `readWordDom` 原先对每段执行一次 `previous.paragraphs.find`，现已改为映射查找；选区计算只遍历相关段落。每次输入仍有全文读取、规范化、模型复制和 JSON 快照成本。
- 渲染已改为按段落标识与内容签名复用节点，并在 DOM 被编辑时失效缓存。普通原生输入提交不再重建全文或重新放置光标；需要重绘时只替换变化段落。输入法组合期间保持 DOM 稳定。
- 后续导入性能迭代已将主应用预检通过的模型一次性交给编辑器，并在单次导入内共用 XML 解析结果，减少重复工作。模型与文件来源绑定，跨次导入重新校验；测量范围与结果见 [DOCX 导入性能对照](word-import-performance.md)。
- DOCX 解压、压缩与 CRC 已迁入 Rust 后台线程；XML 属性处理和写出仍在前端。仍需计入 base64、复制和 IPC 成本后比较端到端收益。

## 可实施的迁移顺序

1. 在独立包核心之上增加 Rust XML/OOXML 与文档模型，定义段落、文字片段、格式、纸张和版本标识；继续用真实 LibreOffice 文件及损坏负例验证内容和拒绝范围。
2. 逐步扩展现有异步命令，保留导入失败时当前文档、首次另存副本、保存冲突与原子保存行为。浏览器预览当前使用 TypeScript 实现；后续可为 Rust 核心增加 WASM 构建，减少两条路径的实现差异。
3. 采用编辑命令和段落增量，而不是逐次输入都向 Rust 发送完整模型。核心返回受影响段落、版本与选区；界面仅更新相关 DOM。撤销历史采用增量或结构共享，避免重复持有全文。
4. 随分页、表格等功能开发，再把字体度量、行分割、分页与表格布局放入 Rust。用同一文档、同一字体和同一机器比较冷启动、打开、输入、保存耗时及峰值内存。

浏览器选区采用 UTF-16 偏移，Rust 字符串采用 UTF-8；协议必须明确字符边界转换，覆盖中文、emoji、组合字符、软换行和跨段选区。版本检查必须避免异步结果覆盖新输入。

文件处理应尽量保持“Rust 读取已授权文件 → 解析”和“Rust 序列化 → 原子保存”。若首版仍把文件 base64 发送到前端再传回 Rust，必须把编码、复制与 IPC 时间计入测量，不能只报告核心函数耗时。

## 与全 Rust 界面的区别

Rust 核心加 Vue 界面属于混合架构。连界面也采用 Rust，需要替换 Vue/WebView 编辑区域，重新实现中文输入法组合、选区、剪贴板、无障碍、字体回退和跨平台渲染。可以作为后续路线，但目前的基准不足以证明它是解决卡顿的必要条件。

当前已在 Linux 工具链中验证新 Rust 包核心及 Tauri 编译接入，并补充包处理层面的性能对照。WASM 目标和完整原生界面的验证环境仍需准备；尚未完成真实 Tauri IPC 的端到端性能测量或新的桌面打包。
