# 文件内容保留：继续研究与迭代

2026-10-14。本轮在四工作区功能完善之后，优先处理实际保存会改变内容或遗漏属性的问题。研究用参考软件与公开源码继续放在独立目录，没有将它们作为产品运行依赖。

## 普通文本框改字保留格式

修复前实际复现：在混合字号、颜色和上下标的文本框中只改一个字，保存后所有字符变成第一段格式；带手动换行的正文还会被重建成不同的段落结构。只比对纯文字，或只比较本应用自己的预览，都无法发现这类损失。

现在对普通文本框的已提交文字计算有预算的 Unicode 差异，在原文字片段上更新内容，同时更新显示模型。多处修改之间的未改文字、原字符属性、段落属性和手动换行均保留；每次提交形成新的基准，连续编辑、撤销和再次保存不会重放旧偏移。

替换文字继承被替换的首字符格式；无选择范围的插入使用当前行左侧格式，行首取右侧。参考程序具有活动文字片段信息，而当前输入框仅提供最终文字，因此这是本应用明确的继承规则，不声称与原生光标行为完全一致。重复文字的删除位置可能有歧义，界面提示核对格式。混合格式正文仍不能增删换行；字段、链接和动画绑定等复杂正文继续保护，不偷偷转成纯文本。表格单元格和备注不属于这次修复范围。

专项覆盖多处改字、中文与 emoji、空行、连续保存、局部格式后改字、撤销重做和过期草稿；真实 Vue 界面还验证下载重开、失败留草稿、Esc 取消与事前拒绝。具体实现及边界见[正文编辑记录](presentation-text-content.md)。

![实际下载重开后保留颜色与上下标](screenshots/text-content-preserved.png)

REA 证据 `ev_b7eb93f59f8bae3d72a8e53eab241314aef7fd9fcdb23d916dbc0ec7228fa0e4`：4 个摘录文件、16 个函数、8,957 个 AST 节点，零解析失败。研究确认选区边界与未修改的片段应分别保留；产品实现使用独立的差异计算与原 XML 增量写回。

## 图表、表格与图片的对象属性

已复现：图表修改一个数值或表格增加一行，数据虽正确保存，原对象的标题、替代文字、点击链接、提示文字和锁定属性却消失。未编辑的导出正常，确认损失来自重建图形对象的路径。

现在重建视觉内容时，保留同类型对象的整个非可视属性容器。当前对象 ID、名称以及跨页关系先处理，再复制该容器；不回填原图表数据、单元格或旧几何。锁定属性的“保留”指文件保存语义，不代表应用已实现所有原软件的交互锁定规则。

实际回归通过 **229 个断言**：三轮改数据、保存并重开；跨页复制中故意制造关系 ID 冲突，验证目标仍正确；标题、替代文字、点击/悬停链接、占位符、锁定与不识别的扩展节点保留；新数据也保留。图片替换是编码器模型级检查，本轮没有增加图片替换按钮。另以 Python ZIP/XML 读取验证了 5 份输出包。

重跑：`node tests/browser/presentation-object-metadata.cjs`。报告在 `test-results/presentation-object-metadata/`，修复前后最小复现在研究目录 `frame-metadata-repro/` 与 `frame-metadata-fixed/`。

REA 证据 `ev_8ff3f6d26ed25604374708718ff4348314474c09a62040081f725bcb01699912`：4 个函数、817 个 AST 节点，确认非可视属性与表格/图表内容分开读写。最终 XML 与跨页关系正确性由上述实际测试证明，不能只凭静态解析推导。

## Word 附件的保存保护

此前检查识别 `o:OLEObject`，却漏掉合法的 `w:objectEmbed`。现在同时检查 Strict/Transitional 命名空间和真实对象父节点，验证内部 `oleObject/package` 关系及非空附件，沿正文实际引用查到页眉、页脚、脚注、尾注和批注。孤立节点、伪标签和外链不冒充内嵌附件；损坏关系无法完成检查时继续要求副本。

新增预检与应用保存流程回归，确认取消保存、切换或恢复标签后，仍需另存副本。这是补齐**风险识别和保存保护**；没有修复办公内核转换附件时的内容损失，也没有执行内嵌附件。

新增 4 组预检与 2 种应用状态回归，相关两个 Node 测试文件共 80 项通过。实际研究样例另覆盖 5 份含真实 OLE 附件的 ZIP 文档，核对节点、关系和附件数据；不将附件被识别等同于内容转换无损。

## 表格中仍未修复的差异

本轮查明 UNIQUE 不支持时会被外层 COUNTA 掩盖，返回看似正常的 1；布尔常量在导入时已转为公式；深度隐藏仍降为普通隐藏。详见[真实诊断与后续条件](calc-compatibility-investigation.md)。没有将这些问题改标为通过。

REA 证据 `ev_e707a012fa44040875a1cd7ff196218a0064da62dee7497bd329587b2073ae82`：5 个文件、16 个函数、3,463 个 AST 节点，零解析失败。参考程序自身也存在深度隐藏被降级的路径，因此对照研究不能代替文件语义核验，更不能直接照搬其行为。

## 最终验证

最终源码通过 **498 项 Node 测试、39 项 Python 测试**，零失败；类型检查与生产构建通过，输出在 `dist/`。专项与回归分别计数，不相加作为总覆盖率：

| 检查 | 实际结果 |
| --- | --- |
| 普通文本框内容 | 92 个断言、13 个保护性拒绝场景、5 组真实界面检查；包含无正文形状首次输入、默认/母版继承及显式零覆盖 |
| 对象非可视属性 | 229 个断言；5 份输出由独立 ZIP/XML 读取器复核 |
| 局部格式回归 | 449 个断言、34 个保护性拒绝场景 |
| 既有混合文字/段落回归 | 22 个混合文字、72 个段落断言、4 组段落界面检查 |
| 复杂 PPTX | 12 份固定原件的保留、编辑和重开检查通过，页面/控制台错误、外网与旧办公引擎请求均为 0 |
| 参考桌面打开 | 两份正文导出共 8 页、两份对象属性导出共 4 页，均成功打开并逐页截图 |

参考桌面检查只证明这些实际文件可以打开和渲染，不证明像素一致，也不是原生编辑后回存。对象属性的首次尝试因无可用 X 显示失败，启用隔离 Xorg 后的一次重试通过；初次失败报告保留。正文实际验收的两份文件另保存精确输入副本，防止后续测试覆盖输出路径造成证据混淆。

验收时又修复了空白形状首次输入被拦截及继承格式不一致的问题：导入时解析未来正文所用的默认段落、行距、段距、基线和文本框设置，仅生成显示基线，不改写原 XML。首次输入、再次修改、保存重开的继承属性一致；显式零仍覆盖默认值。逻辑回归完成后还统一了字段保护提示文字，并再次通过类型检查和生产构建；最终构建晚于全部产品源码变更。
